## The map

**Name:** "Wayfinder map: Advaisor React client v1 decisions" (`bd create -t epic -l wayfinder:map`)

**Destination:** Every product, UX, and technical decision the Advaisor React client needs is settled and recorded on this map, so the follow-up spec effort can start without asking the owner another question.

**Notes (summary):** domain (5 roles, 8-state plan lifecycle, V1–V6 validation, AI students-only); truth precedence `docs/product` → `design.md` → skills; backend contract path and the backend map named as the settled-decision baseline (never reopened here); every HITL ticket resolves only with the map owner; grilling sessions open with the grilling-session setup; UI-shaping tickets invoke ui-ux-pro-max and impeccable per design.md §10 and announce per DS-AI-01; trusted package installs are authorized (owner, 2026-10-01) with a stated reason; one resolution per session, research excepted; refer to tickets by name, never bare id.

**Not yet specified (fog):** spec doc structure and how implementation tickets get cut from it; E2E verification scope (J1/J2 journeys); performance and bundle-split budget per role shell; Arabic string inventory and translation workflow; Storybook story inventory for the ~30-component library; client caching/offline stance for campus networks.

**Out of scope:** writing the frontend spec (a later effort, e.g. via to-spec — the user plans it "later"); building any of the client; reopening backend settled decisions or changing the API contract; redoing design tokens (deviations amend design.md, not this map).

## Execution steps

1. `bd create` the map (epic, `wayfinder:map`, priority 1) with Destination/Notes/fog/out-of-scope as the description.
2. `bd create` each child: `-t wayfinder -l wayfinder:<research|prototype|grilling|task> --parent <map> --no-inherit-labels`, body = `## Question` plus the context needed to work it self-contained.
3. Wire the edges above with `bd dep add`.
4. Fire 7 parallel research subagents (general-purpose, calling the Skill tool with "research"): each claims its ticket (`bd update <id> --claim`), resolves the question from local files and/or web, records the resolution in ticket notes, and closes it. To avoid concurrent map-body clobbering, subagents do not touch the map; the charting session then appends all Decisions-so-far lines to the map in one pass.
5. Verify with `bd ready --parent <map>` (frontier shape) and `bd list -t wayfinder --status open`.
6. Report the map by name, the frontier, and the next step: a work-through session on "App skeleton and demo demolition" (grilling, needs the owner present).
